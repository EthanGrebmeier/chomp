# GQC-03 — bounded model feasibility spike

Status: **GQC-03 feasibility spike complete with a NO-GO for implementing the candidate as production authority.** Same-entry conflict handling and lifecycle/read-completeness proof remain blocking. No application schema, runtime writers or production data were changed. Temporary permissions in existing proof namespaces were restored and fixtures were verified removed. Do not treat the passing local model tests or the bounded experiment as a deployed protocol proof.

## Why this spike exists

The product contract in [the PRD](prd.md) requires independent manual, direct-recipe and scheduled quantities on one grocery row. The current scalar `grocery_items.quantity` and one-to-one scheduled source links cannot represent that. `increment-grocery-list-item.ts` currently performs a read/absolute-write; a stale client can lose an increment. [GQC-02](gqc-02-decision-and-writer-map.md) inventories the other scalar/source writers and their incompatible assumptions.

The archived QTY-02 experiment at checkpoint `36752a9` exercised **real authenticated InstantDB clients** against a dev app: two concurrently acknowledged independent adds left two entries summing to 3 but a writable row projection of 2. An entry-only update could also omit the projection. Its revision-permission proposal is _rejected_, not a compare-and-swap primitive. Those observations motivate removing the writable total; they do not prove the replacement below.

## Related GQC-04 boundary evidence

The [GQC-04 investigation](gqc-04-write-fence.md) now demonstrates a bounded disjoint-namespace permission fence with real SDK clients, including rejection of queued legacy transactions and authorization of updated shared-member flows. A row-only freeze was insufficient. Actual pre-feature-build, native restart/replay and full application dependency-closure validation remain outstanding, so #44 stays open. These boundary results do **not** resolve this document's same-entry conflict, immutable retry, complete-read or source-lifecycle blockers; #45 must not treat the probe's permissive entry writes as a proven production protocol.

## Smallest candidate

- Row owns shopping metadata, list/store, normalized unit and checked/deleted state; **no authoritative scalar quantity**. An entry owns immutable ID, row/list association, quantity, source kind and immutable display provenance; a scheduled entry has a stable source-generation identity. Direct recipe adds use a distinct operation/ingredient ID for every intentional addition; retries reuse that ID. Never use name as identity.
- Query all accessible entries for the row; derive the visible total from the active, finite, nonnegative quantities with the matching normalized unit. A read that is loading, errored, offline without a verified complete snapshot, or missing an expected relation is **not** zero and cannot authorize a destructive write. Checked rows freeze their purchased quantities; source sync cannot create an unchecked delta after purchase.
- Independent adds create independent entry IDs, avoiding a common scalar read/modify/write. Source edits/deselection target exactly their own entry. Whole-row deletion, a move across lists, merging into an existing row, reselecting a previously removed source and removing the last entry require explicit lifecycle rules and are **not** established by this model.
- `gqc-03-model.ts` and its tests exercise the intended reducer, retry identity, exact-source update and fail-closed read _as pure code only_. They do not test SDK persistence, optimistic subscriptions, authorization, a crash, or concurrent edits to the **same** entry. `JSON.stringify` in the test-only helper is not a persistence or authorization mechanism.

## Bounded InstantDB experiment and remaining #45 gates

The owner authorized the existing test app because new InstantDB provisioning is unavailable. `scripts/prove-gqc-03.mjs` refuses to run unless `.env.local` matches the archived authorized dev-app ID **and** `--test-app` is supplied; this verified target is an explicit exception to README's generic warning about `.env.local`. It uses existing `qty02_probe_*` namespaces only, checks deny-all resting permissions, creates random-ID marked fixtures, temporarily changes **only proof namespace** rules, restores the prior rules, and verifies fixtures are gone. It never pushes the application's schema or permissions or writes application entities. Two authenticated SDK clients (plus an outsider) perform transactions; admin reads check server postconditions. Do not run this script against a different app by changing its hard-coded guard.

| Experiment                                                 | Required observation / decision                                                                                                                                                                                                                                                                   |
| ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Concurrent independent adds to the same row                | Both independently identified entries survive, aggregate from a complete read equals their sum; no row scalar is written.                                                                                                                                                                         |
| Repeat an intent vs distinct new intent                    | Same persisted ID cannot count twice; a second intentional add gets a new ID. Establish whether a conflicting same-ID upsert is rejected or may silently overwrite.                                                                                                                               |
| Source edit racing source edit/deselect                    | Establish conflict policy for the **same entry**; stable IDs alone do not prevent last-writer-wins (the archived experiment observed this). Do not claim no lost updated-client edits without a solution.                                                                                         |
| Row plus entry/source changes, invalid link/permissions    | Determine transaction rejection/partial-commit behavior for supported operations and shared-list member vs outsider. Do not assume a transaction makes stale reads serializable.                                                                                                                  |
| Subscription loading, partial relations, offline/reconnect | Determine when a relation is _provably complete_ and whether old cached totals are clearly marked stale; block delete/move/reconcile until safe. `queryOnce` offline failure and warm-cache offline results were observed in the archived memory-transport experiment, not a native restart test. |
| Sync, remove and retry after purchase/deselection          | Verify no resurrection, orphan, duplicate or modification to a second entry under the chosen source lifecycle.                                                                                                                                                                                    |

**Decision / revised proposal:** retain independent entries and a derived-only total as the direction, but **do not start #45's authoritative schema/write implementation** on this proof alone. Next, try a narrowly scoped append-only intent per entry edit (including stable operation IDs and explicit replacement/supersession ordering), or choose a conflict mechanism that can demonstrably reject a stale edit. The read model must never silently claim that one of two acknowledged same-entry edits was preserved. Independently prove a server-verifiable or otherwise fail-closed complete-read contract and source lifecycle before destructive repair/merge. If the SDK cannot provide those guarantees, explicitly choose a visible conflict policy or revisit the architecture; do not restore the writable aggregate or promote the archived revision predicate. #44 separately proves the old-client fence. #51 covers full updated-client/native lifecycle once a safe basic protocol exists. **Closing #43 records a blocking finding, not permission to advance #45.**

## Observations and remaining blocker

`node --env-file=.env.local scripts/prove-gqc-03.mjs --test-app` ran using installed InstantDB core **0.22.185** and real authenticated WebSocket clients with memory-backed storage. Successful run `3e9cd09f-f326-4a70-be7e-4d01aa76d807` (the script prints the structured observations):

- Concurrent separate entry creates both returned `synced`, and the server had two entries totalling **3**. The row scalar was not updated. Repeating the exact same-ID write returned `synced` and still yielded two entries totalling 3. **However, changing the payload at that same ID also returned `synced` and changed the total to 9.** Stable IDs alone do not enforce immutable intent or safe retries.
- A shared-list member created a source-linked entry and updated source and entry together (`synced`); the server total changed from 5 to 6. An outsider's attempted entry create was rejected. An authorized entry update bundled with a forbidden row update was rejected with the total still 3 in this bounded case. These are observations of the temporary probe rules, **not** final list/share permission or general atomicity proof.
- Two members simultaneously edited the **same entry**; both returned `synced`, but the final total was 8, reflecting only one of the two requested source quantities. **This fails a no-lost-updated-client-edits claim.** The candidate cannot ship without a policy/mechanism for conflicting edits (or a deliberately documented, visible last-writer-wins choice).
- With a warm subscription, offline `queryOnce` rejected. An offline edit returned `enqueued` while the server stayed at 8; reconnect replay changed the server total to 9. This is **in-process memory transport**, not device restart/durable intent recovery. Neither an initially empty subscription nor a partial relation was proved to represent a complete set.
- The run ended with proof permissions restored and every fixture verified absent. Another successful exploratory run `eed9cd75-56e7-42b7-bd5a-1ace16fa537e` also restored and cleaned up. No production activation occurred.

The experiment's permissive same-ID update and source rules are deliberately **not** a production permission design. A cached `queryOnce` result, `synced` status or the pure helper's `state: 'complete'` flag is not proof that every authorized entry has loaded. Before #45, design/test a same-entry conflict policy, immutable-intent/retry semantics, real shared-list permissions and a fail-closed completeness contract. Purchase, removal, reconnect after process death, source re-selection and moves remain for a further bounded protocol test or the downstream lifecycle gate (#51). Run `pnpm vitest run plans/grocery-quantity-contributions/gqc-03-model.test.ts` for the local reducer checks; those are separate from SDK evidence. Mark the **spike** complete as a documented no-go, not the contribution protocol proved or production-ready.

# GQC-04 — bounded old-client write-fence investigation

Status: **isolated SDK fence experiment passes; full #44 acceptance remains BLOCKED on actual-build and full-graph validation.** The owner authorized use of the test DB credentials after the preflight. The experiment below installed and removed only per-run proof schema/rules and synthetic fixtures in the hard-coded allowlisted test app. Application schema, application permissions and existing application data were not changed. #44 remains open; no production fence or cutover is authorized.

References: [#44](https://github.com/EthanGrebmeier/chomp/issues/44), [writer inventory](gqc-02-decision-and-writer-map.md), [GQC-03 findings](gqc-03-feasibility.md), [rollout contract](prd.md).

## Findings from the current checkout

Baseline: `5a47684` (pre-contribution application writers; includes the GQC-03 probe).

- `instant.perms.ts` authorizes grocery rows and meal-plan sources by list membership, not a server-enforced generation boundary. Lists permit owner/member updates; shares permit self updates/deletes. Existing `attrs` rules reject creation of unknown attributes; they do **not** reject writes to existing scalar fields or source links.
- Old and updated clients authenticated as the same user can submit indistinguishable operations, such as deleting an existing row or changing a source quantity. A permission predicate over identical identity, record and mutation inputs cannot selectively reject only the old operation. Merely removing scalar quantity from the new UI does not fence source/delete/link writes.
- Rejecting scalar edits alone misses full metadata payloads, source mutations, reconciler repair, list deletion, membership changes and link-only transactions. Restricting all writes on the old authoritative records would also block updated clients that reuse those records and operations unchanged.
- This rules out **unchanged shared write paths**, not every possible same-app architecture. A complete namespace/generation separation might work, but it needs an isolated proof of every reachable dependency and permission boundary. Do not declare same-app separation impossible based only on these static observations.
- #43 closed with a blocking candidate-model finding. A test client may establish boundary authorization, but cannot establish the correctness of the still-unresolved updated-client protocol.

## Candidate boundaries and decision gates

### A. Same app, disjoint authoritative namespaces

The bounded experiment below prototypes the essential separation in per-run proof namespaces. Full-application validation still needs a safely isolated full-schema environment. Freeze all old namespaces/links that can affect the migrated graph, and give updated clients new authoritative row, entry, source, list and membership namespaces with independently enforced membership rules. Do not keep an old writable list/share/source as an authorization or lifecycle dependency of the new graph. Audit recipe/store/category/saved-item links too: a supposedly cosmetic old-record deletion must not cascade or detach required migrated data. Snapshot or migrate dependencies as necessary.

This is a candidate one-time migration, **not** a permanent adapter, dual writer or synchronization bridge. New namespace names and client version claims are not secrets or authentication factors; security still comes from permissions. Test legacy writes using both SDK metadata cached before cutover and schema refreshed after cutover. Prevent unknown attribute creation as well as writes to known legacy attributes.

Accept only if all dangerous old operations are rejected, migrated state is unchanged, and updated shared-member flows remain authorized. If the necessary separation becomes equivalent to rebuilding the entire application graph, compare its risk with a new app rather than quietly expanding scope.

### B. New InstantDB app (fallback proposal, not approved cutover)

A different app ID provides an explicit datastore boundary: old binaries and their queued transactions remain addressed to the old app. Migrate the complete required graph into the new app; configure updated builds and authentication for it; permanently reject legacy application writes in the old app before reopening the new one. Do not forward old queues or bridge writes between apps.

A new app ID is public configuration, not a credential. Normal authorization and the new-client correctness gates still apply. Verify auth provisioning, shared membership, identifiers, links, counts/totals, required external references and recovery. Keep the old app write-frozen during recovery; rolling back to old writers is unsafe. This alternative still requires provisioning, a tested migration and explicit rollout approval. It has **not** been executed or validated here.

## Reproducible validation protocol

1. Provision an empty disposable app and record its ID explicitly as an allowlisted target. Configure test authentication without copying production credentials/users. Export its starting schema/rules, load the baseline application schema/rules and synthetic fixtures only. Never run `push-schema`/`push-perms` against the default environment for this experiment.
2. Build the real pre-feature application from a pinned commit with only isolated environment configuration changed. Record commit, build artifact identifier/hash, platform, SDK version and auth configuration. A hand-written transaction impersonating an old writer is supplemental coverage, not an actual-build substitute.
3. Seed two lists, an owner, a shared member and an outsider; include manual, recipe, scheduled snapshot and standalone items, purchased/deleted history and move destinations. Warm the old client's subscriptions. Disconnect it and queue edits **before** installing the candidate fence. Retain this exact client/cache for reconnect.
4. Apply the candidate schema **and** permissions; migrate synthetic fixtures to its candidate graph. Record the rule/schema payloads and before-state digest. Authenticate updated test clients as owner/member/outsider. Do not add a client-supplied version bypass.
5. Run every matrix case below online and replay the pre-fence offline queue. Record SDK acknowledgements/errors, server rejection details when available and admin-read postconditions. Optimistic UI changes and `enqueued` are not authorization successes. Confirm unrelated migrated records and permissions remain unchanged after rejected multi-operation transactions.
6. Exercise updated flows including shared-member access and outsider/revoked-member denial. Repeat after cold start and schema refresh. Archive redacted structured evidence and exact commands. Tear down fixtures, verify cleanup, restore starting permissions or destroy the disposable app. Fail closed if restoration fails.

## Executed bounded SDK experiment

`node --env-file=.env.local scripts/prove-gqc-04.mjs --test-app` uses installed InstantDB core **0.22.185**, real authenticated WebSocket clients and admin-read postconditions. It is **SDK transaction emulation**, not a historical application binary. `scripts/gqc-04-fence-model.mjs` defines the schema/rules; `scripts/gqc-04-fence-model.test.mjs` tests target guards, namespace separation, rule phases, and cleanup/schema ownership checks.

### Boundary actually tested

- A random run prefix owns **nine namespaces and 61 attributes**: old/new lists, membership records, rows and sources, plus new entries. References stay within one generation; there are no cross-generation refs, user refs or cascades. Auth IDs are scalar membership values. Old rows retain scalar quantity; new rows have no quantity attribute, and new entries carry amounts. This is a schema separation, not a client version flag.
- A negative control starts with legacy member writes allowed, then freezes only legacy rows. The member's row scalar write is rejected, **but source quantity and list name still change**. Freezing grocery rows alone therefore fails the source/list boundary.
- The full candidate freezes create/update/delete on **all four old namespaces**, keeping their member reads, and enables membership-authorized writes on the disjoint new graph. New list owner IDs cannot be changed by an update; new membership creation is owner-controlled; a member can leave. These intentionally small probe rules are **not the application's complete join/share policy**.
- The same user identities run both old-shaped and updated-shaped operations. Namespace names are not secret or a client-attestation mechanism. An authenticated user could deliberately submit updated-shaped operations; this proof is about unchanged pre-feature writer paths, not distinguishing two identical transactions from different binaries.

### Evidence, safety and reproduction

The script prints the run ID and evidence path. It saves the exact temporary schema/rule payloads, matrix outcomes, server error types/statuses and graph hashes in `plans/grocery-quantity-contributions/evidence/gqc04-<run>.json`. Final runs also record script/model SHA-256 and before/restored configuration digests. Admin tokens, auth tokens, application records and original permission payloads are **not** included in committed evidence.

Run only when no other process/person is editing the test app's schema/rules. The API writes a complete rules document; pre-write/read-back checks detect external changes, but are **not** a server-side compare-and-swap lock. The script refuses to overwrite detected non-proof changes. It first denies proof namespaces, explicitly creates only the run's schema, and validates that application schema is unchanged. A mode-0600 local recovery manifest is persisted **before** remote mutations at `tmp/gqc04/<run>.json`; do not discard it until cleanup is verified. The script checks marker/ID ownership and unexpected references before deleting synthetic fixtures, deletes synthetic auth users, removes only its own attributes, restores original rules and verifies the schema/rules against the initial snapshot (excluding server-derived type inference). Both handled failure and success paths run cleanup; any experiment or cleanup failure exits nonzero. Abrupt process termination cannot run `finally`; retain the manifest and use the cleanup command rather than assuming the app is restored. Never remove the hard-coded target guard or use the application's push commands for this experiment.

```sh
node --test scripts/gqc-04-fence-model.test.mjs
node --env-file=.env.local scripts/prove-gqc-04.mjs --test-app
# Only for a run whose local manifest is retained:
node --env-file=.env.local scripts/prove-gqc-04.mjs --test-app --cleanup <run-id>
pnpm lint && pnpm tsc
```

## Remaining blockers and revised rollout recommendation

1. **Actual pre-feature build is still untested.** Local inspection found Xcode and a booted iOS simulator, but no pinned `.app`/`.ipa`/`.apk` artifact under the inspected `dist`, `ios`, `android` paths. This is not a claim that building is impossible. The application imports its real entity schema and real auth bridge; redirecting it to these renamed proof namespaces would change its write paths and would not be an environment-only historical-build test. An actual pinned build must run against a safely isolated **complete application graph**, including old auth configuration and queued data. Do not point it at unrelated existing application records just because the probe credentials work.
2. **Whole-graph separation is unproved.** Recipes/ingredients, stores/categories/saved items, frequent-item events, production list/share/join rules, source reconciliation, cascades, purchase history, move retries and process-death replay are not modeled end to end. The generic source and two move-phase mutations are representatives, not the application's builders. The old→new namespace mapping for all of these dependencies needs design/review before implementing candidate A.
3. **Decision:** unchanged shared authoritative paths and the row-only freeze are a **NO-GO**. Fully disjoint same-app authority is now a _plausible tested primitive_, not an approved architecture or completed old-client fence. Keep candidate A only if the full dependency closure can be isolated and real builds pass the outstanding matrix. Otherwise propose candidate B (new app plus old-app write freeze) to the owner, explicitly approve the changed migration/auth/recovery plan, and validate it. This experiment does not prove that every possible same-app fence is impossible, nor that a new app rollout is already validated.
4. **#44 remains open and #45 remains blocked.** #43's same-entry/read-completeness/source-lifecycle no-go is independent and unchanged. Do not promote these permissive probe entry updates into the authoritative contribution protocol. Closing #44 needs the actual-build evidence required by the issue, or a substantiated architecture no-go with an agreed enforceable revised boundary. No production rollout can advance on this bounded pass alone.
